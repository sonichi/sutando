# holder_lock: one-process exclusion per work root (parent PR, design v5.10)

v5.10 (the claude-local session): the record schema is **2**. Its top-level `pid`/`start` name the process whose liveness fences the root — the owner from `publish` until `attach_consumer`, the consumer after — so a schema-1 reader that rejects the record as `unsupported` still scans exactly that pid and refuses while the consumer lives; the holder's own identity moves to `owner_pid`/`owner_start`, which schema-2 `publish`, `release` and the owner checks validate instead; `consumer` is null or `{pid, start}` and `tombstone` null or `{by, at, reason}`; a schema-1 record keeps its meaning. Three additions, both copies: `attach_consumer(owner, expected, *, pid, start) -> Published`, a compare-and-swap by the holder under the module guard and the §1.8 check that writes the consumer only while the record's bytes still equal `expected` (`LockError("record changed")` otherwise, nothing written; once per record, `LockError("consumer attached")`); `tombstone_consumer(root, expected, *, by, reason) -> Published`, a compare-and-swap under the lock directory's flock by a launcher that proved the pair gone — allowed only when the holder **and** the consumer both verify `False` twice, one second apart, and the bytes still equal `expected`; it writes `consumer: null` and the tombstone and fences the root by the dead holder again, never removes the record, and a held flock, a changed record, a missing consumer or a live or unobserved process is a `LockError`; and `occupancy(root) -> free | held | unobserved`, the one shared tri-state reader (`task_io.lock_held` delegates to it): a non-blocking flock probe released at once, then the record under the **sticky rule** — a live holder, a live consumer or an unverifiable one is never `free`. `_prior_refusal` applies the same rule: a verified-live consumer is `Held("live consumer")`, an unverifiable one `Held("unobserved consumer")`, only a verified-gone consumer passes. `release` stays the holder's; nothing else writes the record. ## What v5 moved to the notifier PR and why

- `children[*]`, `set_children`, reserve-then-spawn, the pending TTL: a record of children either wedges every successor behind a live orphan or releases it while the orphan still acts (the reviewer's findings 1, 2, 5). The notifier makes its children die with it instead, so there is nothing to record.
- Every fence and orphan rule, `authorize_signal` in all forms: signals are the consumer's; with no orphans there is nothing for this module to authorise (finding 6). A record here never names anything but its holder.
- The control-pipe protocol, the watcher and sender lifecycle, `status`'s child liveness: #5629's, specified executably there (finding 7).
- The notifier consumer paragraph: replaced by one sentence in §2 — the notifier publishes a holder record like any adapter.

## 1. API

1. `acquire(work_root, *, install_id, timeout=0.0) -> Acquired | Held | Contended | TimedOut | Unreadable | LegacyRunning`. Under one module lock per process (an acquisition already in progress or an existing owner → `LockError("already owner")`, nothing touched), in this order: the path is normalized lexically, `abspath(normpath(work_root))`, and created component by component from `/`, each opened from the one above (`mkdir`/`open` with `dir_fd`, no path-based `makedirs`) — the root itself is the ONLY thing created under or at the root before `Acquired`; `root = realpath(path)`; the root is opened `O_DIRECTORY` and held; `lock_dir` (§5.1) is keyed by that fd's `(st_dev, st_ino)`; the lock tree is opened and created the same way from the home directory (`0700`), and every directory opened on the way — the home and each component, however it was reached — is checked by walking `..` from its fd and comparing `(st_dev, st_ino)` with the root's, before anything is created under it and again from the new component's own fd right after it is opened; one inside the root (a case alias, a symlinked ancestor, a component swapped or renamed meanwhile) is `LockError("work root contains the lock directory")`, and a component this call just made there is removed first; the lock file is opened relative to the final directory fd, `open(lock, O_RDWR|O_NOFOLLOW)` or, when absent, `O_CREAT|O_EXCL`, and the lock directory's ancestry is checked once more from its fd (a lock file just made under the root is removed, then the same `LockError`); the lock directory fd is kept as `owner.dir_fd`; `file_lock.try_lock_fd` — False → unlock nothing, close, `Contended(holder)` where `holder = read_holder(root)` as it is now (`Missing` while the winner is between its flock and its publish; a `wait` polls through it); True → the lock name in the held directory is the open fd and the lock directory's path still names that directory (else `LockError("replaced")`), then the root is revalidated: `lstat(path)` is a directory and not a symlink, `realpath(path) == root`, and `stat(root)` is the held fd's directory, else unlock, close, `LockError("root changed")`; the same check is the last operation before `Acquired` is returned. Then the prior is read under the flock and decides: `Missing` → `Acquired`; `Valid` with `verify_lineage(pid, start, host)` False → `Acquired` (overwritten on publish); True → unlock, `Held(holder, reason="live holder")`; None → unlock, `Held(holder, reason="unobserved")`; `Invalid` containing any parseable positive pid whose lineage is True or None → unlock, `Held(holder, reason="invalid record naming a live or unobserved pid")`; `Invalid` otherwise → `Acquired` (overwritten on publish); an `OSError` reading it → unlock, `Unreadable(reason)`. `LegacyRunning`: §4.3. `Acquired(owner, prior)`: `owner` is an in-process handle (fd with `FD_CLOEXEC`, `lock_id=(dev, ino)`, `pid`, `start`, and `root_fd`, the held root directory, open for the owner's life and closed last by `release`), never passed to a child, one per process (`LockError("already owner")` otherwise). After `Acquired` the owner acts on its root only through `root_fd` (`os.mkdir(..., dir_fd=owner.root_fd)` and the like): a path renamed away and replaced after the last check is simply a different root, with its own lock on its own inode, and the owner never acts on it. Pins: `HL::test_two_concurrent_acquires_in_one_process_let_exactly_one_proceed`, `HL::test_a_root_replaced_after_the_flock_check_is_refused_before_acquired`, `HL::test_stable_root_identity_holds_through_the_consumers_first_act`, `HL::test_a_case_alias_of_the_home_as_the_root_is_refused_before_anything_is_created`, `HL::test_a_symlinked_ancestor_pointing_inside_the_root_is_refused`, `HL::test_a_component_swapped_for_a_symlink_into_the_root_while_the_tree_is_built_is_refused`, `HL::test_a_checked_directory_renamed_under_the_root_before_mkdir_leaves_nothing_there`, `HL::test_the_lock_dir_moved_under_the_root_before_the_lock_open_leaves_no_lock_there`, `HL::test_a_contended_result_reports_the_record_of_the_lock_it_contended_on`, `HL::test_acquire_publishes_nothing_and_returns_the_prior_under_the_flock`, `HL::test_a_live_or_unobserved_holder_is_held_and_a_dead_one_is_overwritten`, `HL::test_an_invalid_record_refuses_on_a_live_or_unobserved_pid_and_is_overwritten_otherwise`, `HL::test_a_loser_gets_contended_with_the_current_record_or_missing_while_the_winner_is_pre_publish`, `HL::test_a_replaced_lock_file_or_a_changed_root_is_refused`, `HL::test_one_owner_per_process`.
2. `wait(work_root, *, install_id, deadline, poll=0.1, on_tick=None) -> Acquired | TimedOut | Unreadable | LegacyRunning`: the loop over `acquire` for `Contended` and `Held`; `deadline` absolute `time.monotonic()`; `on_tick(elapsed_s, holder)` once per poll, may raise to abandon. The waiter keeps the verified lock-directory fd open for the whole wait and writes `waiting.<pid>` (`"<start> <epoch>\n"`) only through it — temp created `O_CREAT|O_EXCL|O_NOFOLLOW`, fsynced, renamed, and unlinked on return, all `dir_fd`-relative; before each attempt the lock directory's path must still name that fd, else `LockError("replaced")`; each attempt takes the module acquisition lock for that attempt only, never across `on_tick` or the sleep; a second `wait` in the same process while one is active raises `LockError("already waiting")` (same-process overlap is refused, not merged); readers ignore a file whose pid is dead or whose `start` differs from the pid's. Pins: `HL::test_a_waiter_never_writes_or_removes_anything_under_the_work_root_even_when_the_lock_dir_is_redirected`, `HL::test_every_waiter_file_operation_in_wait_goes_through_the_lock_dir_fd`, `HL::test_no_function_acting_after_the_lock_dir_is_opened_does_path_based_io`, `HL::test_each_waiter_owns_its_own_file_and_a_newer_waiter_exiting_first_leaves_the_older_visible`, `HL::test_same_process_overlapping_waits_are_refused`, `HL::test_wait_calls_on_tick_and_honours_an_absolute_deadline`.
3. `publish(owner, adapter) -> Published(record, durable)`: once per owner (`LockError("published")` on a second call); verifies the owner is unreleased, that the lock name in `owner.dir_fd` is `owner.fd` and the lock directory's path still names `owner.dir_fd` (else `LockError("replaced")`), and that the flock is still ours (§1.8); writes `holder` (§2) through `owner.dir_fd` — scan, temp create, write, fsync, rename and unlink all `dir_fd`-relative, no path-based I/O after `acquire` — by the owner's fixed dot-temp `.holder.<dev>-<ino>.tmp` (`O_TRUNC`, so a retry reuses it) + fsync + `os.replace`, overwriting any prior. The rename is the commit: any failure before it (the scan for a crash's temp, the write, the fsync, the rename) raises `LockError`, no record published, the owner still valid — stated residual: if removing the temp also fails, the owner's one temp remains in the lock dir (however many publishes fail, never more than one per owner); the next successful `publish` consumes it by the rename, and an earlier owner's temp is removed by the first `publish` that can, with a logged warning while it cannot; a directory-fsync failure after it returns `Published(record, durable=False)` with a logged warning (the record is on disk, its durability uncertain), never `LockError`. There is no other mutation of the record: the ownership questions of finding 5 reduce to this one write and the one removal in §1.4 — no `set_children` to race a replaced path, no fence for a cleanup path to erase. Pins: `HL::test_failed_publishes_leave_at_most_one_temp_and_the_next_publish_removes_it`, `HL::test_an_earlier_owners_stuck_temp_stays_while_removal_fails_and_goes_once_it_can`, `HL::test_a_lock_dir_moved_aside_and_symlinked_to_the_root_gets_no_write_through_the_path`, `HL::test_a_directory_fsync_failure_after_the_rename_is_published_with_durability_uncertain`, `HL::test_a_failing_directory_scan_before_the_rename_is_a_lock_error`, `HL::test_publish_is_once_per_owner_and_fills_every_field`, `HL::test_publish_overwrites_any_prior_and_leaves_no_temp`, `HL::test_publish_refuses_a_released_owner_a_closed_fd_or_a_replaced_file`.
4. `release(owner) -> Released(record_removed: bool)`: owner process only (`LockError("not the owner")` from any other pid, nothing touched); and a forked child never HOLDS the lock either: `acquire` registers `os.register_at_fork(before=<take the acquisition lock, then the guard>, after_in_parent=<release both>, after_in_child=<fresh locks, no owner, close the inherited lock fd and root fd only while each still matches its recorded (dev, ino)>)`, so no fork lands mid-acquire or mid-release, a child never inherits a lock it cannot take, and a reused fd number is never closed — `FD_CLOEXEC` alone covers only `exec`, and a forked child that keeps the descriptor would keep the flock alive after the owner died; refuses with `LockError("lock lost")`, touching nothing, when the lock name in `owner.dir_fd` is still `owner.fd` but the flock is no longer ours (§1.8); removes `holder` (through `owner.dir_fd`) only if that lock name is `owner.fd` and the record on disk names this `pid`, `start` and `lock_id` (a record that names someone else is left byte-for-byte and `record_removed` is False); then unlocks, closes the lock fd, the lock directory fd and the root fd, and only then marks the owner released. Never call holder_lock from a signal handler: set a flag and release from the main loop. The module guard records its holding thread, so a call that re-enters it on the same thread (a handler interrupting `publish` or `release`) raises `LockError("re-entrant")` at once rather than blocking forever with the lock held. `publish` and `release` do all of this, validation included, inside the module guard: the handle must be this process's current owner object (`owner is _OWNER`: a copy, a rebuilt or a stale handle never acts; `Owner` raises `LockError` on copy, deepcopy and pickle), unreleased, with its root fd present, and its fds must still be the lock file and the held root (by `(st_dev, st_ino)`), else `LockError("released")` before any fd is touched, so a racing second call or a stale handle never closes a reused descriptor or overwrites a successor's record; single use (`LockError("released")`). The lock file is never unlinked, truncated, renamed or replaced by any function here. Pins: `HL::test_a_copied_or_rebuilt_owner_can_neither_release_nor_publish`, `HL::test_a_same_inode_reopen_dup2d_onto_the_lock_fd_makes_publish_and_release_refuse`, `HL::test_a_lock_lost_with_nobody_else_holding_is_refused_too`, `HL::test_a_stale_owner_cannot_release_its_successor_even_on_reused_fd_numbers`, `HL::test_a_signal_handler_calling_release_mid_publish_gets_lock_error_not_a_hang`, `HL::test_racing_releases_inside_the_critical_section_never_both_proceed`, `HL::test_release_after_the_lock_file_was_replaced_leaves_the_record`, `HL::test_release_leaves_a_record_naming_this_pid_but_another_lock`, `HL::test_a_second_release_racing_the_first_never_touches_reused_descriptors`, `HL::test_a_released_handle_cannot_publish_over_its_replacements_record`, `HL::test_release_removes_only_its_own_record_then_unlocks_and_is_single_use`, `HL::test_release_from_a_forked_child_is_refused_and_the_parents_lock_stays`, `HL::test_a_forked_child_holds_no_lock_fd_and_the_lock_is_free_once_the_owner_dies` (fork a child that sleeps, SIGKILL the owner, a successor acquires at once; and `/dev/fd` of the child shows no lock descriptor), `HL::test_a_fork_during_an_acquisition_waits_and_the_child_does_not_keep_the_lock`, `HL::test_a_forked_child_that_reuses_the_fd_number_never_has_it_closed_by_a_grandchild`, `HL::test_a_fork_during_release_cannot_keep_the_flock`, `HL::test_a_child_cannot_inherit_any_module_lock_in_an_unusable_state`, `HL::test_nothing_in_the_module_unlinks_or_replaces_the_lock_file`.
5. `read_holder(work_root) -> Missing | Valid(record) | Invalid(reason, raw_bytes)`: never raises; `Invalid` for missing fields, wrong types or bounds, unsupported `schema`, torn JSON, a non-object. No caller may read `Missing` or `Invalid` as "free": the flock decides. Pin: `HL::test_read_holder_never_raises_and_classifies_every_malformed_shape`.

Platform and `file_lock.py`: `holder_lock` builds on `file_lock` and this PR adds one typed function there, `try_lock_fd(fd) -> bool` (`EWOULDBLOCK` mapped once, in `file_lock`, which stays cross-platform); it does not use `locked_file`. 8. Threat model. `holder_lock` defends against other processes, other owners, and stale or copied `Owner` objects. It does not defend against code in the owning process that closes, dup2s or reopens the module's descriptors: that code can drop the flock while every identity check (object, `(st_dev, st_ino)`) still passes, and a successor may then acquire. One cheap guard keeps such an owner from acting on it: `publish` and `release` first try a non-blocking flock on a fresh open of the lock file through `owner.dir_fd`, which must fail while somebody holds it, and then re-assert the flock on `owner.fd`, which succeeds only if that somebody is this open file description; either outcome otherwise is `LockError("lock lost")`, nothing written or removed. Pins: `HL::test_a_same_inode_reopen_dup2d_onto_the_lock_fd_makes_publish_and_release_refuse`, `HL::test_a_lock_lost_with_nobody_else_holding_is_refused_too`.

## 2. Holder record

1. `<lock dir>/holder`, JSON, every field generated by `publish` except `adapter`: `{"schema": 2, "adapter": str, "pid": int, "start": str, "host": str, "install_id": str, "lock": {"dev": int, "ino": int}, "acquired_at": float, "owner_pid": int, "owner_start": str, "consumer": null | {"pid": int, "start": str}, "tombstone": null | {"by": str, "at": float, "reason": str}}` (v5.10; a schema-1 record has the first eight fields and keeps its meaning). Nothing else: no children, no extra. The notifier publishes one like any adapter (`adapter: "codex-notifier"`).
2. Validation: `pid`, `owner_pid`, `dev`, `ino` are `int` and not `bool`, pids `> 0`; `start`, `owner_start`, `host`, `adapter`, `install_id` non-empty `str` ≤ 512 bytes; `acquired_at` a finite `float`; `consumer` and `tombstone` null or exactly their shape; unknown keys make it `Invalid`. Pin: `HL::test_record_field_types_and_bounds_are_enforced_on_read_and_publish`.
3. A record never authorises acquisition and never names a target for a signal; it says who holds, for `Held`'s explanation and `status`. Pin: `HL::test_no_code_path_reads_a_record_to_decide_acquisition` (spy).

After `Acquired` the caller creates its own directories. ## 4. Install boundary and merge graph

1. `install_id()` is the install location only: `"<distribution>@<realpath of the package directory>"`; the notifier's is `"sutando-src@<realpath of src/>"`. Recorded for `status` and `Held`'s explanation; never compared on the acquire path (a same-location upgrade is a same-install predecessor; a different location that is live is simply `Held`). Pin: `HL::test_install_id_is_the_location_only_and_is_not_compared_on_acquire`.
2. The upgrade order is stop → install → start, owned by the upgrader. Merge graph: this prerequisite → #5660 (the three adapters as thin owners; its second commit also gives `ag2-sparrow-hatch install` and the package installer script their stop-the-package's-adapters → install → start, since the adapters' launch code lives there) → #5665 (rebases on #5660; its keepawake self-upgrade is re-ordered to stop → install → start and is the only unattended upgrader) → #5629. Each of those PRs pins its own order with `test_the_upgrader_stops_then_installs_then_starts`; here only `HL::test_a_start_against_a_live_holder_is_held_and_explains`.
3. Until the upgraders land, one refuse-and-explain at start, no runtime coexistence: after the flock and the prior read, `acquire` reads `<root>/state/connector.pid` ONCE. A single positive integer naming a pid whose lineage is True or None → unlock, `LegacyRunning(pid, path)`; the caller exits 3 "stop the old adapter (pid N), then start"; empty or malformed → refuse the same way with `pid=None` and "… and remove <path>" ONLY while the file is fresh — its mtime within the old writer's create-to-write window, 30 s (an empty file may be the old writer between its `O_EXCL` and its write); an empty or malformed file older than that is a crash leftover and is treated like a dead pid (ignored, never refused — otherwise every unattended start would refuse until a human deleted it); absent or a dead pid → proceed; a live pid whose process started after the file was written (a pid reused since, e.g. after a reboot) is treated as dead; `status` names whatever it finds and WARNS on a stale empty or malformed file. The file is never written or removed by this module; #5660's fresh-dir rule tolerates and removes an attributed dead one. This clause is deleted in the release after #5665 lands. Pins: `HL::test_the_legacy_read_is_through_the_held_root_not_the_path`, `HL::test_a_reused_pid_in_a_leftover_legacy_file_is_ignored`, `HL::test_a_live_or_unobserved_legacy_pid_refuses_and_explains`, `HL::test_a_fresh_empty_or_malformed_legacy_file_refuses_and_a_dead_or_absent_one_is_ignored`, `HL::test_a_stale_empty_or_malformed_legacy_file_is_ignored_and_status_warns` (mtime set 31 s back; the fresh case at 0 s), `HL::test_the_module_never_writes_or_removes_the_legacy_file`.
4. Out of contract, stated: an old writer started by hand after that one read, on a root the upgrader does not know, is not detected; the upgrade order is the control, `status` is the report.

## 4b. Stated limits (the owner's decision, 2026-10-17)

The owner chose to state these as limits of the supported paths rather than design for every installer:

1. The temporary legacy clause (§4.3) refuses a pre-`holder_lock` adapter's empty or malformed `connector.pid` only while the file is fresh (30 s). A live old writer that races that window — creates the file, is slow to write, and is still alive when the new adapter has already decided — is a known limit; it exists only on a host that was not upgraded stop-first, and upgrading stop-first removes it. `status` warns on a stale file; nothing here tries to close the race.
2. Supported upgrade paths are exactly two: the Hatch installer and the keepawake self-upgrade, both stop → install → start, each pinned in its own PR (§4.2). A direct `pip`/`pipx` install or upgrade, a rollback, a process supervisor restarting a unit, and any work root the upgrader does not know must stop the package's adapters by hand before installing; the package README and the adapters' READMEs say so, and `status` reports what is running. Pin: `HL::test_the_readmes_state_the_supported_upgrade_paths_and_the_manual_stop_for_everything_else` (doc scan).

## 5. Lock location and filesystem

1. `lock_dir(root)` is a function of the root's realpath and the uid ONLY: `<home of the effective uid, from pwd, not $HOME>/.local/state/ag2-sparrow/locks/<sha256("<st_dev>:<st_ino>" of the root directory, taken by stat after makedirs)[:16]>` — the key is the root directory's identity, not its path string, so case aliases on a case-insensitive filesystem (macOS `/Users/x/W` and `/users/x/w`), bind mounts and every other spelling of one directory share one key, while two distinct directories never do; the realpath is still used for the revalidation in §1.1 and for `install_id`; no environment variable takes part, because a systemd unit, cron, a Hatch hook and a `nohup` shell differ and two adapters that resolved different dirs would both run. Files: `lock`, `holder`, `waiting.<pid>`. A root that contains its own lock dir (`--work=<that home>` or above it) is refused, `LockError("work root contains the lock directory")`. This is one deliberate amendment to the two-space workspace contract: a host-local, per-uid, never-synced runtime directory for locks, recorded in `docs/workspace-design.md` by this PR; it is not a third state container for anything else. A uid with no passwd entry is `LockError("no passwd entry for uid N")`. Pins: `HL::test_a_uid_with_no_passwd_entry_is_a_lock_error`, `HL::test_lock_dir_is_a_function_of_realpath_and_uid_only_and_ignores_every_env_var`, `HL::test_two_launch_contexts_with_different_environments_resolve_one_lock_dir`, `HL::test_a_root_containing_the_lock_dir_is_refused`.
2. Local filesystem only: `acquire` raises `LockError("not a local filesystem")` when `statfs` reports a network or FUSE type for the lock dir (a network-mounted home); the package README and the adapters' READMEs state the refusal and the remedy (a local home for the service user). Pins: `HL::test_a_network_or_fuse_lock_dir_is_refused` (mocked statfs), `HL::test_the_readmes_document_the_network_home_refusal`.

# Task wedge detection

The user needs a reason and an unblock action under the message that started the work. A live process or a sidecar heartbeat proves neither task progress nor successful delivery. Silence is evidence of **unknown progress**, not proof of failure; detection must never release a claim, retry work, answer a permission prompt, or restart a live session by itself.

## Existing coverage and gaps

This is a source audit, not a deployed-host latency measurement. Durations below are defaults, not guarantees: scheduling, host sleep, unavailable probes, and delivery add delay. The [health fallback](../src/launchd/com.sutando.health-check-fallback.plist) runs every 300 seconds and independently sends configured owner alerts. It cannot alone satisfy a sub-minute signature target.

## Backend evidence

The backend audit inspected `services/agent_tasks/sweeper.py` (defaults and tick), `services/agent_tasks/store.py` (both sweeps), and `services/agent_tasks/fsm.py` (liveness thresholds). The source revision and review reference are retained in the private task report because that repository is not public. Deployment was not verified. The inspected change makes bound/threaded replies count and keeps handed-off working tasks out of the external-silence sweep, so they have one clock. Waiting-input handling remains distinct. These backend clocks do not provide a three-minute local step-row detector.

The current progress API accepts only `queued`, `busy`, or `delegated` for `waiting`, with a 60-character display line. The detector keeps its typed blocker reason locally and projects `phase: "Waiting"` plus a safe reason summary; the publisher omits unsupported `waiting` values. The server accepts this display phase and records progress without changing execution state or clearing a permission blocker. Browser rendering and deployed-server behavior still require live measurement; additional waiting enum values would require a coordinated server/client change.

## Detector integration and measurement

Implementation and measured fixture results are recorded here by the detector change. The acceptance targets are less than 60 s from a supported blocker signature to visible status and less than 210 s for a default 180 s silence threshold. A deterministic clock test establishes policy timing; it does not establish browser-render or network delivery latency. Live proof must timestamp the injected condition, detector observation, accepted progress publication, and first rendered origin-message notice, with owner-DM delivery measured separately. A disconnected route must be reported as an unavailable measurement, never counted as a visible notice.

Keep episode identity task-scoped, deduplicate the owner line, clear on fresh task activity, and suppress transient observations. Publish through the existing task progress path with its original room/message identity. The legacy roomless `wedge` activity row is a global owner-action surface, not a substitute for a status under the task's source message.

### Implemented policy and rollout

`src/wedge_detector.py` is the one state owner. `phase_line.published_status` delegates its already accepted task status to it; the connection-owned publisher retains the task id, execution generation, room and origin message routing. The publisher runs on its existing 10 s clock. `LEDGER_STEP_PUBLISH_ENABLED` now defaults on (an explicit existing override still wins). `WEDGE_SILENCE_SECONDS` in the agent-activity manifest defaults to 180 and may be configured there. A deployment without the progress Action cannot display these notices; its not-deployed response is not success.

The detector considers the latest task-specific activity row, runtime snapshot activity/heartbeat, and phase timestamp. New activity resets a silence episode even if the detector missed the intervening healthy interval. Queued, deliberately waiting and delegated tasks are not diagnosed by silence; completed tasks clear state. A legitimate long tool with fresh task activity remains healthy. With no task heartbeat a slow tool and a hang cannot be distinguished: the notice says **no recent activity**, not that execution failed.

Fresh explicit supervisor limits/prompts and task-bound permission dialogs debounce for 20 s. Shared watcher/stale-core probes come from `wedge_probes.probe_all`. Watcher loss requires repeated observations spanning at least 60 s; an observed recovery or a polling gap over 30 s resets that grace period. This intentionally excludes watcher loss from the sub-minute signature target. Stale core status alone only changes the working summary: it never changes the phase to Waiting or sends an owner DM, because a legitimate long task need not refresh the core status timestamp. Newer task activity suppresses that hint. An unscoped core signature applies only to accepted core-held snapshots, not identified worker tasks or tasks without ownership evidence. Signature text and pane contents are never published; fixed reason/unblock messages are safe for the originating room. Local typed `waiting.reason=blocked` stays local; the deployed wire receives `phase=Waiting` and summary.

State lives under `state/task-wedges` with a per-task lock and atomic replacement. One owner-only result line is reserved after 60 s from the first sustained observation per task episode, never before confirmation and never for a stale-core hint. It enters the normal proactive result/outbox path with `[dm-only]`; it is not a second bridge sender. A crash after reservation can lose that optional DM, but cannot enqueue a duplicate; the origin status retries independently. Existing runtime HITL cards are separate and unchanged. The detector does not generate activity rows, so its own notices cannot mask silence.

### Measured fixture boundary

The real `phase_line` writer and `StepPublisher` were driven with a 10 s deterministic clock. A task with last activity at t=100 published its silence notice at t=280 (180 s), and fresh activity at t=300 published recovery at t=300. Limit/prompt signature tests publish after 20 s of sustained observations; watcher tests require 60 s of consecutive observations, and stale-core tests retain the working phase without owner notices. Six simultaneous production detector processes enqueue exactly one owner notice. These are publication-callback measurements with an accepted mock Action response, **not a deployed browser visibility SLA**. A stopped gateway, disabled publisher, absent supervisor or unavailable watcher probes cannot meet the target. No live service was restarted for this delivered worker task; a post-deployment origin-message round trip and browser timestamp remain required before asserting the <60 s / <210 s end-to-end targets.
